## Findings
1. **Payload fallback was fail-open**
   - `HookEntry.resolveSoPath()` previously returned `/data/local/tmp/libwzry_houdini_selfkill_hook.so` unconditionally when reflection failed.
   - That can execute an attacker-controlled `.so` inside the scoped app.
   - Fixed to require extracted module lib first; fallback now checks existence and size, then throws `UnsatisfiedLinkError` instead of silently loading unknown bytes.
2. **Native patch is the correct 3-byte LSPosed path**
   - `PATCH_RVA = 0x324eef`, `ORIG_BYTES = bf ba 00`, `PATCH_BYTES = e9 bf 01`.
   - This is the proven decision-branch patch, not the rejected `0x5001d0` trampoline hook.
3. **Package scoping belongs in Java, not native**
   - `handleLoadPackage` filters `com.tencent.tmgp.sgame`.
   - Native `/proc/self/cmdline` filter stays dead code because the process is still `<pre-initialized>` at injection time.
4. **Build script has the right package boundary**
   - `provided/` Xposed stubs are compile-time only.
   - `classesDir` is wiped; packaged jar contains only `com\wzry`.
   - `zipalign -c -p 4` and `apksigner verify --verbose` are enforced.

## Residual risks
- The 3-byte patch relies on the already-mapped `libhoudini.so`; it does not neutralize future escalation paths like `abort`, `exit_group`, or other signal numbers.
- `/data/local/tmp` fallback is still permissive; safer long-term is to remove it once extracted-library resolution is proven stable across reboots.
- `native_hook/` remains prototype-only and should not be treated as the production injection path.
